# SwitchMarket — P2P-маркетплейс коллекционных NFT-подарков

## Архитектура

- **Backend**: FastAPI, асинхронный SQLAlchemy + SQLite (легко заменить на PostgreSQL, поменяв `database_url`).
- **Frontend**: чистые HTML/CSS/JS, Telegram WebApp SDK, WebSocket-чат.
- **Инвентарь**: подарки Telegram сейчас существуют как NFT в блокчейне TON. Сервис не выдумывает несуществующий приватный API, а честно читает NFT пользователя через публичный TON-индексер (`tonapi.io`), сверяя адрес коллекции со списком известных коллекций подарков (`app/ton_client.py`). Перед синхронизацией пользователь подключает свой TON-адрес.
- **Роли и доступ (RBAC)**: `UserRole.USER`, `UserRole.VERIFIED`, `UserRole.ARBITER`. К странице сделки `/deal/sm-xxxxxxxx` имеют доступ только `buyer_id`, `seller_id` и любой пользователь с ролью `ARBITER` — то есть доступ определяется ролью, а не одним захардкоженным логином. Присвоить роль арбитра можно только напрямую в базе/через отдельную административную панель с журналом действий — в этом MVP роль выставляется вручную в БД.
- **Эскроу**: реализован как внутренний денежный леджер (`User.balance`, статус `Order.status`) с полным журналом событий `OrderEvent` — каждое действие (заморозка, передача, холд, спор, решение арбитра) логируется с указанием инициатора и не может быть переписано пользователем.

## Важное честное ограничение — прочитайте перед продакшеном

Текущая реализация эскроу — это **централизованный леджер в базе данных**, а не смart-контракт. Это значит, что технически он одинаково пригоден для честной платформы и для мошеннической: тот, кто держит доступ к продакшен-базе, физически может изменить `User.balance` в обход обычных эндпоинтов. Для реальной безопасности пользователей рекомендуется один из вариантов:

1. **TON-смарт-контракт эскроу**: покупатель переводит GRAM (или TON) не на счёт платформы, а на адрес контракта. Контракт содержит логику: перевод продавцу при подтверждении получения, автоматический возврат покупателю по истечении таймаута, и функцию апелляции, вызываемую 2-из-3 подписью (покупатель/продавец/независимый арбитр), а не одной приватной подписью. Такой контракт публично аудируем в explorer'е TON.
2. **Мультиподпись на разморозку** даже в текущей архитектуре: сделать так, чтобы решение арбитра требовало подтверждения вторым независимым арбитром для сумм выше порога, и хранить неизменяемый аудит-лог (например, писать хэши событий во внешний append-only лог или в блокчейн).
3. Как минимум — держать таблицу `OrderEvent` неизменяемой (без UPDATE/DELETE прав у приложения), разделить роль «может резолвить споры» и «имеет доступ к серверу БД» между разными людьми, и публиковать код на GitHub, чтобы пользователи могли проверить логику сами.

## Структура проекта

```
backend/
  requirements.txt
  app/
    main.py            FastAPI приложение, роутеры, фоновая задача авто-завершения холда
    config.py           Настройки (токен бота, JWT-секрет, длительность холда)
    database.py          Async SQLAlchemy engine/session
    models.py             ORM-модели: User, Item, Listing, Order, OrderMessage, OrderEvent
    schemas.py             Pydantic-схемы запросов/ответов
    security.py            Валидация Telegram initData (HMAC-SHA256), JWT, RBAC-зависимости
    crud.py                 Хелперы работы с БД, проверка прав доступа к сделке
    ton_client.py            Чтение NFT-инвентаря пользователя из TON API
    ws_manager.py            Менеджер WebSocket-соединений чата сделки
    routers/
      auth.py                POST /api/auth/telegram, GET /api/auth/me
      catalog.py             Кошелёк, синхронизация инвентаря, лоты
      orders.py              Жизненный цикл сделки, эскроу, споры
      chat.py                REST-история + WebSocket чат сделки
frontend/
  index.html            Разметка SPA (шапка, dynamic island, нижний бар)
  styles.css            Liquid Glass дизайн-система
  app.js                 Роутинг, авторизация, рендер витрины/сделки/чата
```

## Запуск бэкенда

```bash
cd backend
pip install -r requirements.txt
export TELEGRAM_BOT_TOKEN=ваш_токен_бота
export JWT_SECRET=случайная_длинная_строка
uvicorn app.main:app --reload --port 8000
```

## Запуск фронтенда

Отдайте `frontend/` любым статическим сервером (например, `python3 -m http.server 5173` из папки `frontend`) и откройте через Telegram WebApp Button, указывающую на URL фронтенда. `app.js` ожидает бэкенд на порту `8000` того же хоста — при другом хосте поменяйте `API_BASE` в начале `app.js`.

## Что нужно донастроить перед реальным продакшеном

- Указать реальные адреса коллекций Telegram Gifts в `KNOWN_GIFT_COLLECTIONS` (`app/ton_client.py`) — сейчас там плейсхолдеры.
- Заменить SQLite на PostgreSQL для продакшен-нагрузки.
- Добавить рейт-лимитинг и валидацию сумм пополнения баланса (пополнение/вывод GRAM не реализовано намеренно — это отдельный платёжный контур, требующий лицензирования и отдельного аудита безопасности).
- Реализовать выдачу роли `ARBITER` через защищённую административную панель с журналом действий, а не прямыми правками в БД.
